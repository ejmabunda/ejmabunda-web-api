# ADR-007: F1 tier app service cold start workaround

## Status

Superseded by [ADR-008](ADR-008.md)

## Context

This API is - at the time of writing - hosted on an F1 tier app service which does not support Always On. This means the first client to interact with the API after a period of inactivity will have to wait for server to start, about 30 seconds up to around a minute in my experience.

## Decision

Keep the API awake by pinging a public endpoint every 15 minutes or so. This should simulate Always On eliminating cold start. We're going with a GitHub workflow triggered by `on.schedule` on the `main` branch (works only on default branches).

## Alternatives

Upgrade to a basic plan or higher to get Azure-native Always On. Not necessary at the current scale of the API, might consider in future iterations that will benefit from basic tier or higher benefits.

## Consequences

1. Scheduled workflows sit in a queue and execute at a best-effort basis. During periods of high load, scheduled jobs can be delayed or skipped.
2. Pauses after 60 days of inactivity on the repo. Need to re-enable manually by committing.
