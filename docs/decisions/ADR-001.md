# ADR-001: JWT access and refresh strategy

## Status

Accepted

## Context

JWT's are short-lived (10 - 15 minutes per recommendations) hence they are invalidated frequently. This would prompt the user to re-authenticate frequently, not desired in long sessions.

## Decision

A refresh token is created alongside an access token upon successful authentication. When the access token expires, the client submits the refresh token which enables the creation of a new access token alongside a new refresh token. The refresh token is persisted hashed on the database, and is updated on every refresh and will resemble an active session allowing multi-session support without invalidating other sessions. If a refresh token is used more than once, that will signal theft and that refresh token will be rejected. Refresh will have a timeline of 7 days (sliding), a re-authentication is required post-expiration of the refresh.

## Alternatives

1. Set a wide-enough timeline for access tokens. This would create issues when the user wants to log out since JWTs cannot be invalidated, only the expiration date can. In the case where an attacker has access, the further away the expiration date is, the longer the more damage an attacker can make.
2. Creating a new refresh token within a session is possible and won't cause DB space issues, however it makes monitoring active sessions difficult since these would pile up quickly. One refresh token per active session is the better approach.
3. Server-side blocklist for instant revocation (rejected: solves a real problem in priciple, however it's not necessary for a project of this scale)
4. JWT-formatted refresh tokens are not necessary, tokens are DB-checked and this would add complexity to a simple task.

## Consequences

1. There's a 10 - 15 minute window between access tokens which is an acceptable consequence of their stateless nature.
2. JWTs are valid until expiry
3. Abondoned sessions need cleanup
